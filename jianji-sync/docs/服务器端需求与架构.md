# jianji-sync 服务器端：需求与架构

> 状态：设计定稿，待实施 ｜ 2026-11-14
> 定位：简记录账 App 的云端镜像 + AI 只读查询服务。独立项目，与 AgentFlow 无耦合。

---

## 1. 背景与目标

简记（jianji）是本地优先的记账 App，数据在手机 Room（SQLite）里。本项目做两件事：

1. **备份**：接收 App 推送的全量快照，落 PG，带版本历史与误删熔断，可回滚、可恢复到新手机；
2. **AI 只读查询**：提供 HTTP 查询接口与 MCP 服务，让 AI 助手直接拿到**服务端算好的**明细与统计——AI 只引用数字、绝不由 AI 自己计算，从结构上杜绝算错和幻觉。

设计总原则：**App 是唯一写入方，服务器是只读镜像 + 权威计算层**。

## 2. 非目标（明确不做）

- ❌ 服务器→App 的反向同步推送（恢复走显式导出接口）
- ❌ 多设备合并、增量同步、冲突解决（单用户单设备，全量快照足够）
- ❌ AI 写入账本（包括未来的"支付截图→AI 记账"，只预留 `source` 字段口子，不实现）
- ❌ 统计缓存/物化视图（几千行数据 SQL 聚合毫秒级）

## 3. 与 App 的契约

### 3.1 快照格式：直接复用简记的 SnapshotV1

**同步范围 = 账本语义数据**：`records` 全部（含墓碑）+ `categories` 全部（含 emoji/排序/墓碑）。App 的设备级设置（应用锁、自动备份目录、主题）**不进快照**——设备偏好换机时重新选择即可（App 端文档 §5 有完整理由）。

App 端备份编解码器（BackupCodec.kt）已有完整定义，同步原样复用，**服务端按此格式解析**：

```json
{
  "version": 1,
  "exportedAtEpochMs": 1763110000000,
  "categories": [
    { "id": "cat-expense-food", "name": "餐饮", "emoji": "🍜", "type": "EXPENSE",
      "sortOrder": 1, "parentId": null, "updatedAtEpochMs": 1763000000000, "isDeleted": false }
  ],
  "records": [
    { "id": "uuid", "type": "EXPENSE", "amountMinor": 2350, "categoryId": "cat-expense-food",
      "dateEpochDay": 20680, "note": "午饭", "createdAtEpochMs": 1763100000000,
      "updatedAtEpochMs": 1763100000000, "isDeleted": false }
  ]
}
```

要点：
- 金额单位是**分（integer）**，App 原生存储即分，快照全程不换算；分→元的转换只发生在读接口的响应序列化处（见 §5.4），全链路唯一一次
- 含软删除墓碑（isDeleted=true 的记录保留）
- `version` 字段留了格式演化空间；服务端解析未知字段忽略
- `RecordType` 只有两个值：`EXPENSE` / `INCOME`（无转账、无账户概念）

### 3.2 内容指纹（去重判等的唯一标准）

**版本前进 ⟺ 语义内容变化**。canonical 形式：records 按 id 排序、categories 按 id 排序、字段按固定顺序拼接（amountMinor、categoryId、dateEpochDay、id、isDeleted、note、type、createdAtEpochMs；分类再加 emoji、name、**parentId**、sortOrder；parentId 为两级分类父 id，null 与缺失键等价，序列化为空字符串），**排除 updatedAtEpochMs**，sha256 取 hex。

App 端与服务端用同一规则各自计算，双端去重（App 不重复上传，服务端不重复落版）。

## 4. 数据模型（PG，独立 database）

```sql
-- 快照版本表：只追加，永不 UPDATE
CREATE TABLE snapshots (
    id              BIGSERIAL PRIMARY KEY,      -- 版本号，单调递增
    content_hash    TEXT NOT NULL,               -- §3.2 指纹
    record_count    INT  NOT NULL,               -- 含墓碑
    live_count      INT  NOT NULL,               -- 不含墓碑
    max_updated_at  BIGINT NOT NULL,
    payload_gz      BYTEA NOT NULL,              -- 快照原文 gzip
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- 当前版本 = max(id)，不设指针表

-- 镜像表：当前版本的平铺，供查询（每次 sync 成功后事务内重建）
CREATE TABLE records (
    id TEXT PRIMARY KEY, type TEXT NOT NULL,
    amount_minor BIGINT NOT NULL, category_id TEXT NOT NULL,
    date_epoch_day INT NOT NULL, note TEXT NOT NULL,
    created_at_ms BIGINT NOT NULL, updated_at_ms BIGINT NOT NULL,
    is_deleted BOOLEAN NOT NULL
);
CREATE TABLE categories (
    id TEXT PRIMARY KEY, name TEXT NOT NULL, emoji TEXT NOT NULL,
    type TEXT NOT NULL, parent_id TEXT, sort_order INT NOT NULL,
    updated_at_ms BIGINT NOT NULL, is_deleted BOOLEAN NOT NULL
);
CREATE INDEX ON records (date_epoch_day);
CREATE INDEX ON records (category_id);
```

存储估算：每版快照 gzip 后约 100~300KB，滚动保留一年约 60~70 版 ≈ **20MB 以内**。

## 5. 接口

鉴权：两把静态 Bearer Token（环境变量）。`SYNC_KEY`（App，只能调 sync/export）与 `READ_KEY`（AI，只能调只读接口）。走现有 Nginx 反代 HTTPS。Token 的生成与分发：部署时在 `.env` 里 `openssl rand -hex 32` 各生成一把；`SYNC_KEY` 由部署者本人查看后手动粘贴进 App 设置页（自用场景，人就是可信信道），`READ_KEY` 填进 AI 助手的 MCP 配置。泄露/轮换 = 改 `.env` 重启 + App/MCP 侧重配，无用户体系、无注册流程。

### 5.1 POST /api/sync —— App 推送快照

请求：`Authorization: Bearer SYNC_KEY`，body 为快照 JSON，查询参数 `force=false`（默认）。

处理流程（全部在一个事务里，除鉴权）：

1. 解析校验（格式合法性、计数一致性）→ 算 content_hash
2. **去重**：与当前版本 hash 相同 → `200 {status: "noop"}`，不落版
3. **误删熔断**：新 live_count < 当前 live_count × 30% 且当前 ≥ 100 条 → `409 {code: "wipe_suspected", current_live, new_live}`；App 弹确认后带 `force=true` 重传才放行
4. 插入 snapshots 行 → TRUNCATE + 重建 records/categories 镜像 → 顺带执行保留策略清理（§6）
5. `200 {status: "ok", version: <id>, live_count: N}`

### 5.2 GET /api/export?version= —— 恢复导出（SYNC_KEY）

返回指定版本（缺省=当前）的快照原文（gzip 解开）。App 恢复流程用：设置页选版本 → 确认 → 本地全量替换。

### 5.3 只读查询接口（READ_KEY，AI 消费）

| 接口 | 参数 | 返回 |
|---|---|---|
| `GET /api/transactions` | `from`,`to`(YYYY-MM-DD), `type`, `category_id`, `q`, `limit`(默认50,上限200), `cursor` | `{items[], total_count, sum_expense, sum_income}` —— **自带区间合计，AI 不需要求和** |
| `GET /api/stats/summary` | `from`,`to`（或 `month=YYYY-MM`） | `{sum_expense, sum_income, net, count_expense, count_income}` |
| `GET /api/stats/by-category` | `from`,`to`,`type` | `[{category_id, name, emoji, amount, count, pct}]` 按 amount 降序 |
| `GET /api/stats/daily` | `from`,`to`,`type`,`granularity=day\|month` | `[{date, expense, income}]` |
| `GET /api/categories` | — | 分类清单（id/name/emoji/type/isDeleted=false） |
| `GET /api/meta` | — | `{version, content_hash, live_count, last_synced_at, date_range}` 数据新鲜度与覆盖范围 |

### 5.4 响应序列化纪律（防幻觉的核心约束）

- **金额一律输出元，两位小数字符串**：`"amount": "23.50"`。内部 bigint 分 → `f"{minor // 100}.{minor % 100:02d}"`，唯一转换点，单测覆盖
- 所有响应带 `data_version`（快照版本号）与 `generated_at`，AI 引用时可说明数据截止点
- 所有列表响应自带合计/计数，结构上让 AI 没有机会自己算

### 5.5 统计口径：逐条照抄 App 的 SQL，不允许重新诠释

镜像简记 RecordDao 的查询语义，两边数字必须逐分一致：

- 合计/分类/日趋势：`WHERE isDeleted = 0 AND type = ?` + `dateEpochDay BETWEEN`
- 分类合计：`JOIN categories ON c.id = r.categoryId`，`GROUP BY categoryId`，按合计降序（App 不过滤已删分类，服务端照抄不过滤）
- 日期口径 = **业务日期 dateEpochDay**（记账那天），不是录入/修改时间戳；无时区问题（epochDay 是纯整数天）

**验收手段（golden case）**：取 App 里 2~3 个真实月份，App 端统计页数字 vs 服务端 `/stats/*` 响应逐项对账，写进自动化测试。口径对不上=阻断发布。

### 5.6 MCP 挂载：/mcp（READ_KEY）

FastMCP（streamable HTTP）挂在同一服务进程，薄包只读接口，**不引入任何计算**：

| tool | 对应接口 |
|---|---|
| `ledger_transactions` | /api/transactions |
| `ledger_summary` | /api/stats/summary |
| `ledger_by_category` | /api/stats/by-category |
| `ledger_trend` | /api/stats/daily |
| `ledger_categories` | /api/categories |
| `ledger_meta` | /api/meta |

每个 tool 的描述里写死纪律："所有金额与合计一律引用返回字段，禁止自行计算、求和或单位换算；需要新维度时换参数重新调用，不要在已有结果上推算"。

## 6. 快照保留策略

滚动清理，**搭 sync 的车执行**（sync 发生=App 在用=恰当的清理时机），不设 cron：

```
近 7 天        全部保留
7~30 天       每天保留最新 1 版
1~3 个月      每周保留最新 1 版
3 个月以上    每月保留 1 版（月初版，天然对齐按月对账）
```

当前版本（max(id)）永远不删。

## 7. 部署

```
服务器（与 AgentFlow 同机，独立 compose 项目，互不影响）
├── docker-compose.yml    jianji-sync-app（FastAPI）+ postgres:16-alpine（本项目私有库）
├── .env                  SYNC_KEY / READ_KEY / POSTGRES_PASSWORD
└── Nginx                 反代 → https://<域名>/jianji/*（或独立子域名）
```

独立 PG 容器而非复用 AgentFlow 的实例：账本是个人数据，生命周期与工作项目不同，不共享升级与凭据；一个小 PG 容器内存开销 ~50MB，值得。
