# jianji-sync 实施计划

> 状态：规划定稿 ｜ 2026-11-21
> 依据：《服务器端需求与架构.md》《APP端需求与修改.md》（均 2026-11-14 定稿）
> 本文回答"怎么做"：顺序、依赖、每步产出与验收，以及两份设计文档未定死、需在实施时拍板的决策点。

---

## 1. 总体顺序与依赖

```
[服务器 M1] ──→ [App A2 联调] ──→ [M2 只读接口] ──→ [M3 MCP+部署上线]
[App A1]（独立，无依赖，可并行先行）
```

- **服务器先行**：App 的 A2 需要 M1 环境联调（推送→noop→修改→再推→新版本）
- **App A1（无变化不落库）独立**：纯 App 内部行为修正，先做先受益，还能让后续指纹测试更干净
- **M2 在 App 联调后**：golden case 需要 App 真实月份数据已在服务端
- **M3 收尾**：MCP 是只读接口的薄包装，最后挂

每步验收标准全部来自两份设计文档的里程碑表，不另造标准。

## 2. 服务器端里程碑细化

### M1：sync 核心（骨架 + 镜像 + 去重 + 熔断）

**产出**：

| 文件 | 内容 |
|---|---|
| `app/main.py` | FastAPI 入口 + Bearer 鉴权中间件（SYNC_KEY/READ_KEY 双 token） |
| `app/config.py` | 环境变量读取（SYNC_KEY/READ_KEY/POSTGRES_*） |
| `app/canonical.py` | §3.2 内容指纹：records/categories 各按 id 排序、字段固定顺序拼接、排除 updatedAtEpochMs、sha256 hex |
| `app/db/schema.sql` | snapshots（只追加）+ records/categories 镜像 + 双索引，照抄设计文档 §4 |
| `app/sync.py` | POST /api/sync 五步事务：解析校验→算 hash→去重 noop→熔断 409→落版+TRUNCATE 重建镜像+保留策略清理 |
| `app/queries.py`（先只做骨架） | M2 填充 |
| `docker-compose.yml` | jianji-sync-app + postgres:16-alpine（独立库） |
| `requirements.txt` | fastapi / uvicorn / asyncpg / fastmcp，全部钉版本 |
| `tests/` | canonical 单测 + sync 集成测试（见 §4 测试策略） |

**M1 验收**（设计文档 §9）：
1. 同快照重推 → `200 {status:"noop"}`，snapshots 不新增行
2. 伪造清空（live 从 200 → 5）→ `409 wipe_suspected {current_live, new_live}`；`force=true` 重传 → 落版成功
3. 落版后镜像 records/categories 与快照逐行一致

**实现决策（文档未定死，实施时按此执行）**：

- **补一个 `GET /api/versions`**（SYNC_KEY）：App 端文档 §3.6 恢复流程需要版本列表，服务器文档漏了这个接口。实现为：`{versions: [{id, created_at, live_count, record_count}]}`，按 id 降序、最近 50 条。挂 M1 做（App A3 联调依赖它）
- **镜像重建**：`TRUNCATE records, categories` + `executemany INSERT`，几千行毫秒级，不上 COPY 协议（数据量用不上）
- **熔断判断**：`new_live < current_live * 0.3 AND current_live >= 100`（30%/100 条阈值，来自设计文档 §5.1）
- **保留策略**：单条 SQL 窗口函数（`row_number() over (partition by date_trunc('day'/'week'/'month', created_at) order by id desc)`），分三段删；当前版本 max(id) 永不删
- **快照上限**：请求体 > 20MB 直接 `413` 拒绝（与 App 端 §7 上传前检查呼应，双保险）
- **gzip**：Python `gzip.compress(json.dumps(...).encode())` 存 BYTEA，export 时解压返回

### M2：只读接口 + 口径对账

**产出**（`app/queries.py` + `app/money.py`）：

1. 六个接口照设计文档 §5.3 实现表（transactions/summary/by-category/daily/categories/meta）
2. `money.py`：`f"{minor // 100}.{minor % 100:02d}"`，全链路唯一分→元转换点，单测覆盖
3. 响应纪律：所有金额 = 元两位小数字符串；所有响应带 `data_version` + `generated_at`；列表自带合计
4. 统计口径逐条照抄 RecordDao：`WHERE is_deleted = false AND type = ?` + `date_epoch_day BETWEEN`；分类合计 JOIN 不过滤已删分类

**M2 验收（golden case）**：App 里挑 2~3 个真实月份，App 统计页数字 vs `/api/stats/*` 响应逐项对账，写成自动化测试；对不上 = 阻断发布。

### M3：MCP 挂载 + 部署

**产出**：

1. FastMCP streamable HTTP 挂 `/mcp`（同进程），六个薄工具照设计文档 §5.6 映射，工具描述写死"禁止自行计算/求和/换算"纪律
2. 部署：Will 服务器（与 AgentFlow 同机、独立 compose 项目）、Nginx 反代、`.env` 三钥（openssl rand -hex 32）
3. `SYNC_KEY` 手动粘贴进 App；`READ_KEY` 填进 AI 助手 MCP 配置

**M3 验收**：claude code 通过 remote MCP 查到与 App 统计页一致的数字。

## 3. App 端里程碑（jianji 仓库，摘要）

按 App 端文档 §9：

- **A1**：`LedgerRepository.updateRecord`（kotlin:124）+ `renameCategory`/`updateCategory` 加"无语义变化不落库"守卫；验收 = 改回原值保存后 `updatedAtEpochMs` 不变、Room Flow 不发射
- **A2**：`data/sync/` 包（SyncSettings 扩展 / SyncClient OkHttp / 指纹 / 三触发点：启动、退后台 30s debounce、手动）+ 设置页"云端同步"区块；验收 = 真机记一笔 → 退后台 30s → 服务器出现新版本
- **A3**：熔断 AlertDialog（409 → 确认 → force 重传）+ 从服务器恢复（版本选择 → 二次确认 → 事务内全量替换 → 清 lastSyncedHash）

## 4. 测试策略与双端一致性

**最大风险 = 双端指纹不一致**（App 的 Kotlin canonical vs 服务端 canonical.py）。对策：

- fixture 用 JSON 文件固化（`tests/fixtures/canonical_cases.json`：输入快照 + 期望 sha256）
- **同一份 fixture 双端各测**：服务器端 `jianji-sync/tests/fixtures/`；App 端 `app/src/test/resources/sync-fixtures/`。fixture 变更 = 两边同步提交（fixture 文件头注释写明镜像位置）
- fixture 至少覆盖：空账本、含墓碑、note 含 emoji/中文/换行/引号、数字排序陷阱（"10"<"9"，必须按字符串逐字节排序——两端的 sort 实现要按 byte/char 码位，Kotlin `sortedBy { it.id }` 与 Python `sorted(key=lambda x: x["id"])` 对 ASCII 一致，非 ASCII 需 fixture 明确验证）、amountMinor 为 0

**集成测试**（sync 流程/熔断/保留策略）：需要真 PG。沙箱无 docker 的环境下，纯函数单测（canonical/money/解析校验）在本地跑，集成测试脚本带到 Will 服务器上执行（`docker compose up postgres + pytest`）。部署文档里写清这一步。

**golden case 数据**：从 App 导出 2~3 个真实月份（CSV + 快照各一份），fixture 化存 `tests/golden/`，M2 对账测试的输入。

## 6. 风险清单

| 风险 | 对策 |
|---|---|
| 双端指纹规则漂移 | fixture 双端镜像测试（§4）；改 canonical 规则 = 双端同提交，历史 hash 会变，需接受重新全量上传一次 |
| 统计口径重新诠释 | 口径照抄 RecordDao SQL + golden case 阻断发布 |
| fastmcp 版本升级破坏 streamable HTTP | requirements 钉死版本；升级单独提 commit 跑 M3 验收 |
| App 恢复旧版本后服务器"比本地新" | 设计已定：指纹不同即新版本，追加落版不拒绝——无需处理，写测试确认行为 |
| 保留策略误删当前版本 | SQL 里显式 `id <> max(id)` 条件 + 集成测试覆盖 |
| 20MB 快照炸内存 | 双端检查（App 上传前跳过 + 服务端 413） |
