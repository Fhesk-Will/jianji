# jianji-sync 实施计划

> 状态：规划定稿 ｜ 2026-11-21
> 依据：《服务器端需求与架构.md》《APP端需求与修改.md》（均 2026-11-14 定稿）
> 本文回答"怎么做"：顺序、依赖、每步产出与验收，以及两份设计文档未定死、需在实施时拍板的决策点。

---

## 1. 总体顺序与依赖

```
[服务器 M1] ──→ [App A2 联调] ──→ [M2 只读接口] ──→ [M3 MCP+部署上线]
[App A1]（独立，无依赖，可并行先行）
```

- **服务器先行**：App 的 A2 需要 M1 环境联调（推送→noop→修改→再推→新版本）
- **App A1（无变化不落库）独立**：纯 App 内部行为修正，先做先受益，还能让后续指纹测试更干净
- **M2 在 App 联调后**：golden case 需要 App 真实月份数据已在服务端
- **M3 收尾**：MCP 是只读接口的薄包装，最后挂

每步验收标准全部来自两份设计文档的里程碑表，不另造标准。

## 2. 服务器端里程碑细化

### M1：sync 核心（骨架 + 镜像 + 去重 + 熔断）

**产出**：

| 文件 | 内容 |
|---|---|
| `app/main.py` | FastAPI 入口 + Bearer 鉴权中间件（SYNC_KEY/READ_KEY 双 token） |
| `app/config.py` | 环境变量读取（SYNC_KEY/READ_KEY/POSTGRES_*） |
| `app/canonical.py` | §3.2 内容指纹：records/categories 各按 id 排序、字段固定顺序拼接、排除 updatedAt、sha256 |
| `app/db/schema.sql` | snapshots（只追加）+ records/categories 镜像 + 双索引，照抄设计文档 §4 |
| `app/sync.py` | POST /api/sync 五步事务：解析校验→算 hash→去重 noop→熔断 409→落版+TRUNCATE 重建镜像+保留策略清理 |
| `app/queries.py`（先只做骨架） | M2 填充 |
| `tests/` | canonical/money/校验单测 + smoke_http.py 服务器冒烟 |

**验收（M1）**：同快照重推 → noop；伪造清空 → 409 → force 放行；重推幂等。

**实施时拍板的决策**：

1. **补 `GET /api/versions` 接口**——App 端恢复流程（§3.6）需要版本列表，设计文档 §5.3 只列了 AI 只读接口。挂 M1 一起实现（SYNC_KEY 保护），返回 `[{version, record_count, live_count, created_at}]` 倒序。
2. **双端 fixture 分发方式**：同一份 `canonical_cases.json` 放服务端 `tests/fixtures/`，App 端 `test/resources/sync-fixtures/` 镜像一份（内容一致），改规则 = 双端同提交 + fixture 重生成。对账测试各自消费同一文件。
3. **镜像重建用 TRUNCATE + executemany**：几千行毫秒级，不折腾 COPY。
4. **集成测试环境**：沙箱无 docker，纯函数单测本地跑；集成测试出脚本，Will 服务器执行（`docker compose up -d jianji-sync-db` + `python tests/smoke_http.py`）。
5. **快照导出接口的默认行为**：`GET /api/export` 不带 version 返回当前版本（App 恢复流程需要）。

### M2：只读接口 + 对账

**产出**：

| 文件 | 内容 |
|---|---|
| `app/queries.py` | transactions / stats / categories / meta（§5.3 全部接口） |
| `app/money.py` | 分→元唯一转换点 + 单测（含 9 位整数边界） |
| `tests/golden/` | App 真实月份 CSV + 快照 fixture；对账测试：服务端 stats 响应 vs App 统计页数字 |

**验收（M2）**：golden case 逐项一致。

**实施时拍板的决策**：

1. **统计口径的 SQL 化**：把 App RecordDao 的 SQL 逐条翻译成 PG 版（口径 = 业务日期 BETWEEN + isDeleted=0），不许重新诠释。翻译前先把 RecordDao 相关查询全列出来核对。
2. **金额转换纪律的测试化**：money.yuan 的单测含「异常输入拒绝」用例（负数、非整数、非数值），从结构上防止将来有人"顺手"在 SQL 里做换算。
3. **data_version/generated_at 字段**：所有 stats/transactions 响应带上（§5.4 纪律），golden case 对账时一并校验。
4. **分页方式**：transactions 用 cursor（dateEpochDay+id 复合键），不用 OFFSET（个人账本量小，但口径正确优先）。

### M3：MCP 挂载 + 部署

**产出**：

| 文件 | 内容 |
|---|---|
| `app/mcp.py` | FastMCP streamable HTTP 挂载，6 个 tool 薄包只读接口（§5.6） |
| `docker-compose.yml` | app + postgres:16-alpine（独立 PG，不复用 AgentFlow 的） |
| `Nginx 配置片段` | README 里给出（路径前缀 /jianji/） |

**验收（M3）**：claude code 通过 remote MCP 查到与 App 统计页一致的数字。

**实施时拍板的决策**：

1. **fastmcp 版本**：钉 2.8.0；升级单独提 commit 跑 M3 验收。
2. **READ_KEY 的分发**：手动填进 claude code 的 MCP 配置（.mcp.json 或对等物），不走任何在线注册流程。
3. **部署验收**：Will 执行（服务器 + Nginx + .env 密钥生成），沙箱无权限触达生产环境。

## 4. 测试策略

**纯函数层（沙箱可跑，无环境依赖）**：

- canonical 指纹：8 个 golden case（空账本 / 单记录 / 乱序输入 / updatedAt 排除 / note 变化 / 非 ASCII / 墓碑 / 收支混合 + 分类字段差异）
- money：9 个正常值 + 负数拒绝 + 非整数拒绝
- validate：每个校验规则一条拒绝用例 + 合法快照放行

**双端对答案（核心中的核心）**：

- 同一份 `canonical_cases.json`，服务端 pytest 与 App 端 Kotlin 测试各自消费，全绿 = 规则对齐
- fixture 的 expected_hash 由独立参考实现生成（gen_fixture.py 里的 REF_* 实现，不 import 被测代码），实现错了 fixture 不会跟着错
- 改 canonical 规则的 PR 必须双端同提交 + fixture 重生成，CI/本地跑双端测试（明确验证）、amountMinor 为 0

**集成测试**（sync 流程/熔断/保留策略）：需要真 PG。沙箱无 docker 的环境下，纯函数单测（canonical/money/解析校验）在本地跑，集成测试脚本带到 Will 服务器上执行（`docker compose up postgres + pytest`）。部署文档里写清这一步。

**golden case 数据**：从 App 导出 2~3 个真实月份（CSV + 快照各一份），fixture 化存 `tests/golden/`，M2 对账测试的输入。

## 6. 风险清单

| 风险 | 对策 |
|---|---|
| 双端指纹规则漂移 | fixture 双端镜像测试（§4）；改 canonical 规则 = 双端同提交，历史 hash 会变，需接受重新全量上传一次 |
| 统计口径重新诠释 | 口径照抄 RecordDao SQL + golden case 阻断发布 |
| fastmcp 版本升级破坏 streamable HTTP | requirements 钉死版本；升级单独提 commit 跑 M3 验收 |
| App 恢复旧版本后服务器"比本地新" | 设计已定：指纹不同即新版本，追加落版不拒绝——无需处理，写测试确认行为 |
| 保留策略误删当前版本 | SQL 里显式 `id <> max(id)` 条件 + 集成测试覆盖 |
| 20MB 快照炸内存 | 双端检查（App 上传前跳过 + 服务端 413） |
